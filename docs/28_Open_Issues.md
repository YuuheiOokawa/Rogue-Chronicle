# 28. 未決事項一覧（Open Issues）

## 目的
仕様上の未決事項を無視せず一元管理する。設計は止めない方針のため、各課題には合理的な推奨案を「仮採用」して設計を継続している。
決着した課題は状態をClosedにし、決定内容を `29_Decision_Log.md` へ転記する。

## 記載ルール

| 項目 | 内容 |
|---|---|
| 課題ID | ISSUE-NNN |
| 状態 | Open（未決・仮採用で進行中）/ Closed（決着済み） |
| 決定期限 | このフェーズ開始までに決める、の目安 |

---

## ISSUE-001: 正式アプリ名の最終確定
- 状態: Open / 決定期限: Phase 12（Vercel公開）まで
- 背景: 仮称 Rogue Chronicle のまま設計中。候補10案は 00_Project_Overview.md に記載。
- 選択肢: (A) Rogue Chronicle継続 (B) 和名案（深淵年代記 等） (C) 造語案（Everdelve 等）
- 推奨案: A（仮採用中, DEC-001）
- 推奨理由: ゲーム性との一致、リネームコスト回避。公開前に商標・既存サービス重複の確認のみ行う。
- 影響範囲: リポジトリ名、メタタグ、タイトル画面、ドメイン。

## ISSUE-002: パスワード再設定（メール送信基盤）の導入時期
- 状態: Open / 決定期限: Phase 13（運用改善）
- 背景: メール/パスワード認証を採用するが、再設定にはメール送信基盤（Resend等）が必要。MVPでは未導入。
- 選択肢: (A) MVPから導入 (B) 正式公開後に導入し、それまでは問い合わせ対応 (C) メール認証ごと廃止しOAuth先行
- 推奨案: B（仮採用中）
- 推奨理由: MVP期間の主導線はゲストプレイ。メール基盤はコスト・実装量に対して初期利用者が少ない。
- 影響範囲: API-007、users周辺、14_Authentication_Design.md。

## ISSUE-003: 効果音・BGMの導入範囲
- 状態: Open / 決定期限: Phase 10（UI/UX改善）
- 背景: MVP範囲では音は最小限（△）。音なしでも成立するUI設計としている。
- 選択肢: (A) 完全無音でMVP公開 (B) 効果音のみ（タップ・ダメージ・報酬の5〜10種） (C) BGM含む
- 推奨案: B
- 推奨理由: 効果音は打鍵感・報酬の快感に直結し費用対効果が高い。BGMは容量・ライセンス管理コストが大きい。
- 影響範囲: 設定画面（音量）、アセット調達、user_settings。

## ISSUE-004: マスタデータ変更時のアクティブランの扱い
- 状態: Open / 決定期限: Phase 3（マスタデータ・DB）
- 背景: ラン進行中にマスタ（スキル倍率等）を変更すると整合性が崩れる恐れ。
- 選択肢: (A) ラン開始時のマスタversionをrun_stateに記録し、ラン中は開始時点のマスタ値スナップショットを参照 (B) メンテナンス時にアクティブランを強制終了し補償（ソウルシャード） (C) 常に最新マスタを適用
- 推奨案: MVPはB、将来Aへ移行（仮採用中）
- 推奨理由: Aは実装コストが高い（マスタ値のラン内スナップショットが必要）。個人開発MVPではリリース頻度をメンテウィンドウに寄せるBが現実的。
- 影響範囲: dungeon_runs、master_data_versions、12_Database_Design.md、リリース手順。

## ISSUE-005: ゲストアカウントの有効期限・掃除ポリシー
- 状態: Open / 決定期限: Phase 13
- 背景: ゲストは登録なしで作成できるため、放置レコードが蓄積する。
- 選択肢: (A) 最終アクセスから180日で匿名ゲストを物理削除 (B) 無期限保持 (C) 90日で削除
- 推奨案: A
- 推奨理由: Cookieの実質寿命と釣り合い、復帰導線を過度に絶たない。データ量・個人情報保有の最小化にも沿う。
- 影響範囲: users、削除バッチ（Vercel Cron）、プライバシーポリシー記載。

## ISSUE-006: 消耗品（アイテム）のMVP採用範囲
- 状態: Open / 決定期限: Phase 7（報酬・スキル・装備）
- 背景: 戦闘コマンドに「アイテム」があるが、種類を増やすとバランス・UIコストが増える。
- 選択肢: (A) ポーション系3種のみ（HP回復小/大、状態異常治療） (B) 攻撃アイテム含む6種 (C) MVPでは削除
- 推奨案: A（仮採用中、CORE_SPEC §5準拠）
- 推奨理由: 「回復手段の保険」というローグライトの緊張緩和に必要十分。攻撃アイテムはスキルと役割が重複。
- 影響範囲: 戦闘UI、ショップ・宝箱の報酬テーブル。

## ISSUE-007: 防具・アクセサリーのドロップ範囲
- 状態: Open / 決定期限: Phase 7
- 背景: MVP目安は「武器10種」。防具・アクセの扱いが要件上曖昧。
- 選択肢: (A) 防具3種+アクセ3種を最小実装（スロットは3枠とも稼働） (B) 武器のみ（防具・アクセは将来）
- 推奨案: A（仮採用中）
- 推奨理由: 装備スロット3枠のUI・データ構造を最初から作る方が後付けより安い。種類は最小でよい。
- 影響範囲: equipmentマスタ、宝箱・ショップ抽選、18_Skill_Design.md。

## ISSUE-008: チュートリアルの実装方式
- 状態: Open / 決定期限: Phase 10
- 背景: 初回離脱防止の要。専用短縮ダンジョン（5階層）か、通常ラン+ガイド吹き出しか。
- 選択肢: (A) 通常ダンジョンの初回ランにステップガイドを重ねる (B) 専用チュートリアルダンジョンを別途作る
- 推奨案: A
- 推奨理由: 専用ダンジョンはマスタ・分岐の追加コストが高い。ガイドオーバーレイはUI層だけで完結し、スキップも容易。
- 影響範囲: user_settings（チュートリアル進行フラグ）、SCR-301/302のガイド表示。

## ISSUE-009: 複数端末同時プレイの厳密な排他
- 状態: Open / 決定期限: 正式公開後
- 背景: MVPは楽観ロック（version）による「後勝ち+競合検知」のみ。同時操作を能動的にブロックはしない。
- 選択肢: (A) 楽観ロックのみ（仮採用中） (B) セッション単位のラン操作ロック（アクティブデバイス1台制）
- 推奨案: A
- 推奨理由: 実害は「自分のランを自分で壊す」範囲に限定され、ERR_CONFLICT_VERSIONで検知・再同期できる。
- 影響範囲: auth_sessions、API共通処理。

## ISSUE-010: バランスシミュレーションの実施タイミングと合格基準
- 状態: Open / 決定期限: Phase 11（テスト）
- 背景: 数値バランス（勝率目標: 初見10-20%、熟練40-60%）は机上の初期案。
- 選択肢: (A) Phase 6完了時からオートプレイ・シミュレータを常設しCIで回す (B) Phase 11でまとめて調整
- 推奨案: A
- 推奨理由: バランス崩壊の発見が遅いほど手戻りが大きい。domain層が純粋関数なのでシミュレータは安価に作れる。
- 影響範囲: scripts/simulate.ts、21_Test_Design.md。

## ISSUE-011: PWA化の実施時期
- 状態: Open / 決定期限: 正式公開後
- 背景: 将来PWA化を想定。MVPではmanifest等の準備のみ。
- 推奨案: 正式公開後、リテンション施策として実施（ホーム画面追加導線・プッシュ通知はさらに後）。
- 影響範囲: next-pwa等の導入、オフライン時の挙動設計（サーバー権威と衝突するため範囲限定）。

## ISSUE-012: 戦闘ログ（battle_logs）の保存粒度
- 状態: Open / 決定期限: Phase 6（戦闘システム）
- 背景: 全ターンの全行動を保存するとログが肥大化する。不正調査・バグ調査には一定の粒度が必要。
- 選択肢: (A) 戦闘単位で全ターンのactionLogをJSONB 1行に集約、30日保持（仮採用中） (B) ターン単位で行保存 (C) 保存しない（seed+入力列から再現）
- 推奨案: A（将来、seed再現方式Cへの移行を検討）
- 推奨理由: 1戦闘1行なら行数は現実的（1ラン約15行）。seed再現方式は理想だがリプレイ実装が前提。
- 影響範囲: battle_logs、削除バッチ。

## ISSUE-013: 宝箱・イベント経由のソウルシャード獲得が未配線
- 状態: Closed（Phase 8で解消。DEC-292参照） / 決定期限: Phase 8（永続強化）
- 背景: docs/05 §5.4は「宝箱・イベント平均+5」をearned.soulShardsの目安として記載しているが、
  Phase 7実装ではAPI-503（宝箱開封）・API-506（イベント選択）がearned.soulShardsを加算していない
  （戦闘勝利分は統合検証時に発見・修正済み。DEC未採番、コード内コメント参照:
  `src/app/api/v1/runs/current/battle/actions/route.ts`）。宝箱・イベントは相対的に少額（+5程度）の
  副次収入のため、Phase 7完了の必須条件からは外し本Issueとして記録する。
- 選択肢: (A) API-503/506にearned.soulShards加算を追加する (B) 現状のまま据え置き、Phase 8の
  永続強化バランス調整時にまとめて対応する
- 推奨案: B（仮採用中）
- 推奨理由: 主要収入源（戦闘勝利）は既に正しく機能しており、影響は軽微。Phase 8で永続強化コスト
  （upgrade_nodes）とソウルシャード収支を一体で見直す方が手戻りが少ない。
- 影響範囲: src/app/api/v1/runs/current/treasure/open/route.ts、src/app/api/v1/runs/current/event/choose/route.ts。
- 解消内容（Phase 8、DEC-292）: 選択肢(A)を採用。API-503（宝箱開封）は開封確定時に、API-506（EVENT/BLESS/CURSEの
  選択確定時、HEAL/STORYの自動解決分岐は対象外）にそれぞれ`earned.soulShards += 5`を追加した。
  STORYは既にselect-node.tsで+5済みのため二重加算を避けている。curlによるE2E確認で、宝箱開封後に
  earned.soulShardsが期待どおり+5されることを確認済み。

## ISSUE-014: 実績のrun内条件（runLevel/runRelicsHeld/runGoldHeld）はAPI-106でprogress表示ができない
- 状態: Open / 決定期限: Phase 8以降（player_progress拡張時）
- 背景: achievements.condition.typeのうちrunLevel/runRelicsHeld/runGoldHeldは「1ラン内の瞬間最大値」
  （finalize時点のrun_state由来）であり、player_progressには対応する永続追跡列（例:
  bestRunLevel/bestRunRelicsHeld/bestRunGoldHeld）が存在しない。実績解除判定自体（evaluateAchievementCondition）
  はfinalize時点のPlayerStatsSnapshotで正しく行えるが、API-106（実績一覧取得、docs/13 §4.2）は
  「現在の永続データからprogressを再算出」する必要があり、これら3種は再算出不能。
- 選択肢: (A) player_progressにbestRunLevel等の列を追加し、finalize時に都度更新する
  (B) 現状のまま据え置き、一覧画面ではprogress=0固定（未解除時）・解除済みはprogress=goalとして表示する
- 推奨案: B（仮採用中。src/server/usecases/achievement/achievement-view.tsで実装）
- 推奨理由: 実績解除自体は正しく機能する。一覧画面の進捗表示は付加情報であり、MVPでは0/goal表示でも
  致命的ではない。列追加はPhase 8以降のバランス調整とあわせて行う方が手戻りが少ない。
- 影響範囲: src/server/usecases/achievement/achievement-view.ts、src/app/api/v1/achievements/route.ts、
  prisma/schema.prisma（PlayerProgress、将来列追加時）。
